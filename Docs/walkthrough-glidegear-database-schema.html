Core Entity Details

Product (Product)

Idint PKAuto-increment primary key
NamestringProduct name
DescriptionstringProduct description
PricelongAmount in cents, avoids floating-point errors
QuantityInStockintInventory count, deducted on order
BrandstringBrand, used for filtering
TypestringType (Boards/Hats/Gloves/Boots)
PictureUrlstringImage path
💡 Price uses long (cents) instead of decimal to avoid floating-point precision issues, standard practice in financial systems.

Basket (Shopping Cart)

Idint PKAuto-increment primary key
BasketIdstringUUID, corresponds to Cookie value
ClientSecretstring?Stripe ClientSecret, used for frontend payment
PaymentIntentIdstring?Stripe PaymentIntent ID, links to order
ItemsListShopping cart items list (navigation property)
Business methods:
basket.addItem(product, quantity) — increments quantity if exists, otherwise adds new
basket.RemoveItem(productId, quantity) — removes entry when quantity reaches zero

OrderItem (Order Item)

Idint PKAuto-increment primary key
OrderIdint FKForeign key → Order.Id

Design Points (Interview FAQs)

1. Why doesn’t OrderItem use foreign key to Product?
Prices change over time; historical orders must preserve checkout-time price. Snapshot design ensures financial data immutability.

2. Why doesn’t Basket use UserId foreign key?
Shopping cart must work for unauthenticated users; uses random BasketId + Cookie for anonymous cart functionality.

3. Why use long (cents) for price instead of decimal?
Avoids floating-point precision errors; finance-industry standard; frontend divides by 100 to display dollars.

4. Why is Address a separate table instead of embedded?
User can save multiple addresses (current version supports one); separate table leaves room for future extension.
